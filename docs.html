03資料怎麼統整

原始資料是 event 表，每一列是「某組、某工站、某件產品」的一次作業。

欄位意思範例有沒有用到
group_id組別G23分組
product_id產品編號，前綴是場次TEST1-P01判斷場次
station_id工站ST01–ST09分工站
start_time / finish_time開工／完工時間2026-11-14T13:16:46經過時間、偵測新資料
duration_sec作業秒數（Cycle Time）64.1各站平均 CT
status作業狀態COMPLETED只取已完工
wip_before_start / wip_after_finish站前齊套數／完工後累計9999 / 1尚未使用

統整步驟

  1. 篩選：只保留 status = COMPLETED 的紀錄。
  2. 決定場次（同老師的 getTestRoundFromProductId）：TEST2-P01 → 第 2 次測試，舊版 TEST-P01 → 第 1 次測試，沒有 TEST 的 P01 → 正式實作。
  3. 切成產線：依「組別 + 場次」分組，每一組合是一條獨立的產線。G23 有第 1、2 次測試，就是兩條線，因為每一場的流程和熟練度不同，混在一起算沒有意義。
  4. 找這一場的流程：從老師的 station_flow 表找，順序同老師的頁面：本場（G23-T2）→ 前面幾場（G23-T1）→ 組別（G23）。
  5. 再分工站：每條線依 station_id 收集每一件的作業秒數、開工和完工時間。
  6. 找終點站：流程圖裡沒有「往下一站」連線的工站（有好幾個時取編號最大）。這一場沒有流程設定時，用有資料的最後一站。

項目算法在哪裡算

排名依產線 Cycle Time 由短到長。選了場次時只跟同一場次的組比網頁

名稱：「總耗時 ÷ 產出組數」是產線 Cycle Time（平均產出間隔，含首件暖機）。老師監控中心的橫幅稱它為「節拍時間」，統計表則稱「Cycle Time」，兩者是同一個數字。嚴格的節拍時間（Takt Time）是「可用生產時間 ÷ 需求量」，是由需求決定的目標；目前系統沒有需求量，所以不計算。

四捨五入：加總用十進位精確計算，最後才四捨五入到小數 1 位，跟手算一致（81.15 → 81.2）。瓶頸站和平衡率用未四捨五入的值算，避免好幾站四捨五入後同分而選錯。

特殊情況：終點站還沒完工時，用有資料的最後一站試算，並標「未到終點」；一場的資料跨越超過 3 小時，標「跨天資料」，不列入排名。這兩個規則都跟老師的頁面一致。

def round_of(product_id: str) -> str:

    m = re.match(r"^TEST(\d+)-", s)

def flow_for(flows_by_key, group, rnd):
    # 本場 → 前面幾場 → 組別（同老師 timer.html、監控中心的候選順序）
    keys = [f"{group}-T{r}" for r in range(n, 0, -1)] + [group]
    for k in keys:
        if flows_by_key.get(k):
            return k, flows_by_key[k]

def terminal_station(edges):
    # 沒有任何「往下一站」連線的工站；有好幾個時取編號最大
    nodes = {a for a, _ in edges} | {b for _, b in edges if b}
    terminals = sorted(st for st in nodes if not any(a == st and b for a, b in edges))
    return terminals[-1] if terminals else None
